Troubleshooting

Common issues encountered while configuring, running, or contributing to the BL Weather Report workflow, and how to resolve them. If your issue isn't listed here, open an issue on GitHub.

Configuration & Connections

Workflow errors out with no rainfall events found

The rainfall-event fetch (task id get_events_data) sets raise_on_empty: true, so if EarthRanger has zero rainfall_rep events for your selected Time Range, the workflow raises an explicit error rather than completing with empty outputs. You'll see this surface as:

Task instance 'get_events_data' raised ValueError('No data returned from EarthRanger for get_events')

This means EarthRanger genuinely returned no data for the period you selected — it isn't a connection or permissions problem. Widen the time range and re-run, or confirm rainfall_rep events exist for that period directly in EarthRanger.

EarthRanger connection fails or times out

Verify the server URL, username, and password configured in the Data Source Connection. Confirm you can log into that same EarthRanger instance directly in a browser with the same credentials. Credentials aren't validated at setup time, so an invalid password only surfaces as an error once the workflow actually runs.

Google Earth Engine connection fails, or NDVI charts are missing

Confirm the private key file uploaded in the Google Earth Engine connection is a valid service-account JSON key with Earth Engine access enabled. If the key is invalid or lacks permissions, calculate_ndvi_range fails for every ranch and no NDVI charts are produced.

Amboseli geospatial layers or the Word template fail to download

The three Amboseli GeoPackages and the Word report template are fetched from fixed Dropbox share links in spec.yaml. These links carry an expiring share token (st= parameter); if a link has been rotated or revoked on Dropbox's side, fetch_and_persist_file will exhaust its 3 retries and fail. This isn't a workflow configuration issue — the URLs in spec.yaml would need to be refreshed.

Map & Charts

Rainfall map PNG is blank, cut off, or missing in the Word report

The map's html_to_png conversion (convert_map_png) waits 40 000 ms for the basemap tiles to load before capturing the screenshot — far longer than the 10 ms wait used for the plotly charts, which render client-side without external tile requests. On a slow network this can still be insufficient; if the map image is consistently incomplete, the tile servers may be slow or rate-limiting requests during that run.

Some rainfall stations are missing from a chart or the map

Rainfall is aggregated by raingauge_station, taken from the event detail field Rain gauge station. If an event's details don't include that field (or it's blank), the row won't be attributed to a named station in the aggregated output — check the underlying rainfall_rep event in EarthRanger for a missing or malformed detail value.

A station's rainfall total looks too low despite readings being logged

Each event's overall reading combines the digital and manual gauge values with the digital reading taking priority (digital_raingauge falling back to manual_raingauge, both falling back to 0). If a ranger logs a value in the wrong field, or a non-numeric value is entered, convert_columns_to_float coerces it to 0 rather than raising an error — check the raw event details for that reading.

Monthly stacked chart shows months out of order or missing colours

Month order comes from a dedicated calendar-month lookup task (not derived from the data), so months always appear Jan→Dec regardless of which months have data. Colours come from the Blues_r colormap applied to the month name column — if this looks wrong, check that time values parsed correctly during date decomposition rather than the chart configuration.

NDVI chart is missing for one ranch, or shows no historic band

NDVI is calculated separately per ranch by splitting the Amboseli conservancy boundaries on the R_NAME column. If a ranch's polygon is very small, has invalid geometry, or Earth Engine returns no imagery for the selected NDVI Method and time range, that ranch's chart can come back empty while others succeed — this is expected fan-out behaviour, not a workflow-wide failure.

Report & Dashboard

Word report is missing an image, or fails to generate

generate_weather_report runs with validate_images: true, which checks that every expected chart/map/NDVI image exists before populating the template. If any upstream chart or PNG conversion failed or was skipped (e.g. due to an empty rainfall dataset), report generation will fail rather than produce a document with blank placeholders.

Word report always says "Generated by Ecoscope"

This is expected — generated_by is a fixed string in spec.yaml, not looked up from the EarthRanger user who ran the workflow. If per-user attribution is needed, this would require a change to spec.yaml.

Dashboard is missing the NDVI charts

This is expected — the dashboard (gather_dashboard) is wired to exactly four widgets: the rainfall map, the overall rainfall chart, the monthly rainfall chart, and the rainfall-by-station table. Per-ranch NDVI charts are written as standalone output files and embedded in the Word report only.

No outputs written / can't find results

All outputs are written to the directory specified by the ECOSCOPE_WORKFLOWS_RESULTS environment variable. Confirm it's set and points to a directory the workflow process can write to.

Contributing & CI

These apply if you're modifying the workflow itself (spec.yaml, test-cases.yaml, or the generated ecoscope-workflows-bl-weather-report-workflow/ directory) and opening a pull request.

Generated files differ from committed files in ecoscope-workflows-bl-weather-report-workflow

The generated workflow directory is out of sync with spec.yaml. Run the recompile script locally and commit the result:

pixi run --manifest-path pixi.toml --locked bash -c "./dev/recompile.sh --update"

test-cases.yaml references a calculator task that doesn't exist in this workflow

The current test-cases.yaml still contains calculator parameters (a, b, operation) left over from the workflow scaffold — spec.yaml has no task with that id. If you're updating test cases, replace these with parameters for the tasks this workflow actually exposes (workflow_details, time_range, gee_client, er_client_name, ndvi_method, and the NDVI trend grouping unit).

Found wildcard version (*) in requirements or Found local file channel (file://) in requirements

In spec.yaml, every dependency under requirements must pin an exact version and use a remote conda channel — wildcard versions and local file:// channels are only valid for local development, not for CI using published packages.

VERSION.yaml (...) must be greater than main branch (...)

Bump MAJ/MIN/PATCH in ecoscope-workflows-bl-weather-report-workflow/VERSION.yaml so it's strictly greater than the version on main before opening or updating a PR.

Workflow tests fail in CI but pass locally (or vice versa)

test.yml runs test cases against all of ubuntu-latest, macos-latest, and windows-latest. If a test only fails on CI, check whether it depends on EarthRanger credentials or the Earth Engine key (EE_KEY_JSON) being available as secrets, or on OS-specific path handling.
